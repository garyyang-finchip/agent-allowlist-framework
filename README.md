# Agent Whitelist Framework (AWF)

Scoped allow and deny lists for agents and other objects: who admits or refuses what, for which activity, on which grounds, with what result.

AWF defines whitelists and blacklists together. Both are lists of one kind that differ only in polarity, `ALLOW` or `DENY`. A list has typed members (accounts, registered agent identities, groups, runtime instances, artefacts such as a model or tool version, named services). A list has no effect on anybody until a consumer binds it for its own actions.

AWF fixes how admission and refusal are expressed, checked and given effect. It does not fix whom to admit, which evidence to require, or what makes an agent good or bad.

## What it defines

- **Four objects of a list.** Scope (where a rule is meant to apply), List (members with a polarity and a manager), Criteria (one immutable version of the rules, with the code and configuration of the module that computes them pinned) and Entry (one subject in an enumerated list, with its basis, validity window and status).
- **Typed subjects.** A reference carries its kind, chain, namespace and identifier. Six kinds are defined; further kinds need no registration.
- **Four ways to have members.** Written by the manager, shown by proofs against a committed set (with proofs of absence for sorted sets), computed from criteria by an evaluator, or derived from another list, either as a plain reference or by extension to objects related to a listed one.
- **Binding.** A consumer, or the adopter it named, declares which lists it uses on the `ALLOW` and on the `DENY` side, for which actions, and what happens on a conflict, on no match and on the undetermined. Nothing is assumed in favour of a request.
- **One standard result.** A list answers `MATCH`, `NO_MATCH` or `UNDETERMINED`. A binding answers `ALLOW`, `DENY`, `NOT_APPLICABLE` or `INDETERMINATE`. The adopter's disposition (`PROCEED`, `REFUSE`, `DEFER`, `PROCEED_RESTRICTED`) is kept apart from both.
- **Standing.** `ALLOW` is never returned for an actor unless the caller was verified as entitled to act for the subject.
- **Three versions.** Rules, list state and binding are versioned separately, and an assessment names all three, so that an earlier result can be recognised as no longer current.
- **Dimensions of evidence.** An open vocabulary (identity, credential, principal, runtime, inference, performance, relation, activity, safety, dispute, reputation, liveness, other lists, designation) and one form every piece of evidence is stated in. No list has to use any of them.

Out of scope: scores and rankings, identity and assertion systems, proof systems, what a refusal means for work already done or for payment, verification of other chains.

## What the reference implementation covers

| Part of the specification | Implemented | Reported through ERC-165 |
| --- | --- | --- |
| Registry: scopes, criteria, enumerated lists and entries, notice, objection, management | yes | yes |
| Committed sets with membership and non-membership proofs | yes | yes |
| Predicate lists with pinned evaluators | yes | yes |
| Derived lists: reference, pin, related-object extension | yes | yes |
| Guard: bindings, standing, assessment, admissions, state digest | yes | yes |
| Zero-knowledge set proofs | no | no |
| Signed assessment receipts | no | no |
| Standing and evidence for objects on other chains | no, such results are undetermined | no |

Registry and guard have no owner, no upgrade path and no privileged account. Limits: chains of derived lists up to 4, fan-out of a relation up to 8, 1,500,000 gas per module call, 8 lists on one side of a binding, 16 actions per binding.

The two example modules read an assertion registry, a task ledger and an address-anchored identity registry through narrow views. The tests run the relation source against the reference registry of address-anchored agent identities (vendored, unmodified) and check that the views of the evaluator have the selectors of the full interfaces of the assertion registry and the task tender kernel. See [test/vendor/README.md](test/vendor/README.md).

## Build and test

Requires [Foundry](https://github.com/foundry-rs/foundry) (tested with 1.7.1), Node 20 or later and Python 3.

```sh
bash scripts/setup.sh          # fetches forge-std into lib/
forge test                     # 134 tests: unit, worked cases, fuzz, vectors
cd tools && npm install && node awf.mjs check && cd ..
python3 scripts/make-filing-package.py --check
```

`node tools/awf.mjs check` validates every example document against its schema, recomputes every identifier and confirms that examples and vectors are what the rules produce. The tool is written from the specification and uses none of the Solidity code; the Solidity tests replay its vectors, so identifiers, set proofs and outcome rules are implemented twice.

`python3 scripts/make-filing-package.py --check` verifies that the specification quotes the interfaces exactly, that every value it quotes is in the vectors, that the tables it works out follow from the rules, and that every asset is linked.

## The three worked cases

**Case A, who may bid for a task is decided by criteria.** A task board binds one `ALLOW` list whose members are computed: a credential of level 2 bound to the controller of the agent identity, and two accepted deliveries by that controller within ninety days. A qualified agent bids. An agent with a lower credential, a bid without history, a bid by somebody else in the name of the qualified identity, a bid by a new owner of the identity and a bid after the credential expired are refused, each for its own reason and none by being put on a blacklist. An unreadable source defers the bid instead of refusing it.

**Case B, a group refuses listed agents, with notice.** A group binds a `DENY` list with a notice period. An entry that states a fact commits to its evidence, is on record during the notice period without effect, can be objected to, and then takes effect. The account bound to the refused identity is another object: it is refused only after the group adopts, in its binding, a second list derived by that relation. Naming an uninvolved account as successor relates nobody; taking the identity over and binding to it does. When the entry is revoked the derived refusal ends with it.

**Case C, a service combines an allow list with two deny lists.** One of the deny lists is a committed set, for which the caller proves absence. The case covers a conflict, no match, an undetermined side, a borrowed identity, an earlier result after a revocation and an earlier proof after a new commitment. A second binding of the same service refuses an excluded tool version without concluding anything about the agent that asked.

All three are tests (`test/AWFCases.t.sol`) and all three are what the evidence run executes on a live network.

## Gas

Measured on a local node with the gas rules in force before state creation was repriced (EIP-8037, which Sepolia has used since October 2026). Under that pricing deployments cost several times more; the evidence run takes its limits from the node.

| --- | --- |
| Deploy `AWFRegistry` | 3,072,818 |
| Deploy `AWFGuard` | 3,080,052 |
| Declare a scope | 94,326 |
| Register criteria with a module | 173,177 to 188,771 |
| Create a list | 107,632 to 169,844 |
| Add an entry | 117,504 to 139,467 |
| Revoke an entry | 50,054 to 52,962 |
| Commit a set | 51,294 to 85,494 |
| Adopt a binding (one to three lists) | 388,405 to 567,818 |
| Amend a binding | 191,778 |
| A gated action through the example consumer, one enumerated list | 116,875 to 133,736 |
